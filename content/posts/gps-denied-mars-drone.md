## 前言

在 Maker 社群裡，我們常看到光鮮亮麗的成品展示，卻很少有人願意攤開失敗的細節。這篇來自 Reddit r/raspberry_pi 的分享，正是一份珍貴的「失敗報告」——一支參加 **ISRO（印度太空研究組織）機器人挑戰賽**的團隊，用 Raspberry Pi 5 打造了一架完全自主、無 GPS 的火星探測無人機，然後在比賽中遭遇了一連串殘酷的現實打擊。

他們沒有掩飾問題，而是逐一拆解每個環節的失敗原因，這份坦誠讓整篇文章成為所有想踏入自主飛行領域的人的必讀教材。

## 專案概述

### 挑戰規則

ISRO Robotics Challenge 的自主無人機組別要求極為嚴苛：

- 在模擬火星地形的 **20×20 公尺**場地中飛行
- **完全無 GPS**、無外部定位基礎設施（禁止 UWB 信標、外部攝影機等）
- 起飛後**零人為介入**
- 需自主導航至預設航點、偵測並避開障礙物
- 辨識地面彩色標記，最後精準降落於指定區域

簡單來說：把無人機丟進一個模擬火星的沙坑，按下啟動鍵後就只能在旁邊看著它自己飛。

### 硬體配置

| 元件 | 型號 / 規格 |
|------|-------------|
| 飛控 | Pixhawk 6C（ArduPilot） |
| 伴飛電腦 | **Raspberry Pi 5**（8GB） |
| 視覺 | RPi Camera Module 3 |
| 測高 | TFmini-S LiDAR |
| IMU | BMI088（Pixhawk 內建） |
| 視覺定位（原計畫） | Intel RealSense T265 |

### 軟體堆疊

- **Python + OpenCV**：光流與視覺處理
- **pymavlink**：與飛控的 MAVLink 通訊
- 自製航點導航器：死算推估（dead reckoning）+ 視覺校正
- **YOLOv8n**（ultralytics）：地面目標偵測

## 技術亮點：六大真實教訓

### 1. 🔌 T265 視覺定位的全面崩壞

團隊原本計畫用 Intel RealSense T265 做 V-SLAM 室內定位，卻在 RPi 5 的 Bookworm 64-bit 系統上踩到大坑：

- `librealsense` 無法順利編譯，核心模組（DKMS）衝突不斷
- 即使勉強跑起來，在模擬火星的**均勻褐色沙地**上，追蹤漂移嚴重到無法使用
- 最終在比賽前三天緊急放棄，退回光流 + 死算推估方案

> 💡 **社群回饋**：強制 T265 走 USB2 模式反而能讓驅動更穩定；`librealsense` v2.54.1 分支搭配手動修補核心標頭檔可成功編譯——但代價是兩天的苦工。

### 2. 🏜️ 光流在火星地形上形同虛設

光流演算法需要地面紋理才能計算位移，但模擬火星表面是**均勻的紅棕色沙地**，幾乎沒有可辨識的特徵。團隊嘗試加裝向下照射的 LED 陣列來製造陰影紋理，在實驗室有些效果，但比賽場地的燈光條件完全不同，定位漂移依然嚴重。

> 「沒有好的定位來源，超過 5 公尺的自主導航基本上是不可能的。」——原作者

### 3. 📏 LiDAR 測高遇到地形起伏

TFmini-S 在平地表現尚可，但場地中的小石塊和高低差讓讀數出現尖峰，導致無人機上下抖動。團隊的卡爾曼濾波器只寫了一半、未經測試就上場。

> 💡 **社群建議**：使用**互補濾波器（Complementary Filter）** 結合 LiDAR（精確但有雜訊）與氣壓計（平滑但會漂移），並對 LiDAR 做 5-7 樣本的中值濾波來消除尖峰。

### 4. 🐌 YOLOv8n 在 RPi 5 上僅 2-3 FPS

以 1280×720 全幀跑 YOLOv8n，純 CPU 推論只有 **2-3 FPS**，加上光流與 MAVLink 同時運行，CPU 溫度飆破 **85°C**。團隊手上其實有 **Hailo-8L** 加速器，卻來不及整合。

社群成員回報的數據令人振奮：

| 方案 | FPS |
|------|-----|
| RPi 5 CPU + 1280×720（原始） | 2-3 |
| RPi 5 CPU + 640×480 + ONNX 優化 | 8-10 |
| RPi 5 + **Hailo-8L** + YOLOv8s | **25+** |

### 5. ⏱️ MAVLink 通訊延遲與 Python GIL

MAVLink 迴圈以 ~10Hz 運行，但實際指令到回應的延遲不穩定，導致航點校正經常遲到、無人機衝過頭。串口設定 921600 baud 應該夠快，團隊懷疑是 Python 的 **GIL（全域直譯器鎖）** 在單一行程中造成時序問題，應改用多行程架構或將關鍵路徑移至 C++。

### 6. 🏟️「實驗室能飛」≠「比賽能飛」

所有元件在 4×4 公尺的測試空間都運作正常，但 20×20 公尺的比賽場地有不同的光線、地面材質，還有鄰近隊伍無人機產生的氣流干擾。**環境差異**是壓垮系統的最後一根稻草。

## 值得肯定的部分

並非一切都是失敗：

- **ArduPilot 的基礎穩定控制**表現出色，手動與定高模式飛行穩定
- YOLO 在有足夠處理時間時，**成功辨識了 4 個地面標記中的 3 個**
- 機械結構紮實，全程無墜機、無硬體故障
- **RPi 5 作為伴飛電腦**確實有能力，只是需要適當優化與 AI 加速器

## 心得與延伸

這個專案完美示範了「**系統整合**」才是自主機器人最大的挑戰。單一模組各自運作良好，不代表它們能在同一顆 SoC 上、在真實環境中協調工作。

### v2 版本計畫

團隊已規劃下一代改進：

1. 整合 **Hailo-8L** 做加速推論
2. 改用 **ORB-SLAM3** 做視覺里程計
3. **多行程架構**分離視覺、通訊與導航
4. 互補濾波器改善測高穩定性
5. 在多種環境下進行充分測試

### 社群實用建議

對於想嘗試 GPS-denied 導航的 Maker：

- 🔗 **UWB 超寬頻定位**（如 Decawave DWM1001）可達 ~10cm 精度，但需比賽規則允許外部設施
- 🎯 **ArUco 標記**可做低成本的視覺定位校正
- 🗺️ 善用已知位置的偵測目標作為「視覺地標」來修正死算漂移
